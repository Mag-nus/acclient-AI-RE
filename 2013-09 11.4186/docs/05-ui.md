# The UI Framework and In-Game Windows

Target: acclient.exe 11.4186 (September 2013). Line references are into
`../acclient.c` and `../acclient.h` unless noted.

> **Revision note.** Written in a first pass, then verified line-by-line in a
> second pass. The widget-ID table was incomplete, the `gm*UI` registration story
> was wrong (there are two registries, not one), and several structural details
> needed correction. The second pass also added the input/keybinding system, the

## 1. Class hierarchy

The framework is a fully **retained-mode** widget tree.

`UIListener : IInputActionCallback` (acclient.h:33568) is the root — every UI
participant can receive input actions and UI messages.

`UIRegion : UIListener` (acclient.h:33608) adds spatial identity: a `Box2D m_box`,
`m_zlevel`, two `Graphic*` (image plus alpha mask), an `m_alphaBlendMod`, flags
(`m_visible`, `m_transparent`, `m_bBlockClicks`, `m_bDrawAfterChildren`,
`m_bTooltip`), a `BlitMode`, a parent pointer, a `UIObject *m_object`, and
children in a `HashList<UIRegion*>` — a hash table fused with a doubly-linked
list, giving O(1) lookup plus explicit z-sorted paint order.

`UIElement : UIRegion` (acclient.h:33782) is the widget class proper: drag state,
a focus child pointer, a `MediaMachine`, its `LayoutDesc*` and `ElementDesc`, the
current state ID and `StateDesc*`, a `PropertyCollection`, tooltip text, a
per-element cursor DID, a listener `HashSet<UIListener*>`, and a 25-bit flag word
beginning at **acclient.h:33713**.

`UIObject` is at **acclient.h:33832** and `MediaMachine` at **acclient.h:33873**
(the first pass cited 33753 and 33814).

## 2. Layouts, states, and skins

`LayoutDesc : DBObj` (acclient.h:33881) has `GetDBOType()` returning decimal
**35** (acclient.c:149546). Note that 35 == `0x23`, so "type 35" and "type 0x23"
are the same number — and `0x23u` is exactly what is passed to
`QualifiedDataID` in `CreateRootElementByDataID` (acclient.c:155062) and to
`DBObj::GetByEnum(_layoutEnum, 5, 0x23u)` in `CreateChildElementByEnum`
(acclient.c:155094).

**The DID range is separate: `0x21000000`–`0x21FFFFFF`.**
`MasterDBMap::DivineType_Internal` returns 35 for that range
(acclient.c:89806–89809). So: DB type = 35 = `0x23`; DID prefix = `0x21`. The
same table gives StringTable 37 ↔ `0x23xxxxxx`, ActionMap 39 ↔ `0x26xxxxxx`,
String 41 ↔ `0x31xxxxxx`, Font 46 ↔ `0x40000000`–`0x40000FFF`, FontLocal 47 ↔
`0x40001000`–`0x40FFFFFF`.

A layout holds a hash of `ElementDesc`s. Each `ElementDesc : StateDesc` carries
`m_type` / `m_engineType`, a base-layout DID for inheritance (flattened by
`LayoutDesc::InqFullDesc`), a default state, edge anchors (`m_leftEdge`,
`m_topEdge`, `m_rightEdge`, `m_bottomEdge`), and child descs. Each `StateDesc`
(acclient.h:33640) gives x, y, width, height, zlevel, a `PropertyCollection`, and
an array of `MediaDesc*`.

`UIElementManager::CreateElementRecursiveFromPartialDesc` instantiates the tree
by looking up `m_engineType` in `m_classCreateMethodTable`.

Sizes are in *virtual* coordinates: `UIObject` keeps `m_nVirtualX/Y/Width/Height`
plus `m_vScale`. **`m_vGlobalScale` does not rescale anything** — an earlier draft
said it did. It is written once, to the one-vector, in the `UIElementManager`
constructor (acclient.c:156187) and is **never read** anywhere in the file. The
cited line 152990 is inside `UIElementManager::RefreshEvent` (body 152979),
which resizes the root element to `GetDisplayWidth`/`Height` in pixels.

## 3. The MediaMachine is a bytecode interpreter

`MediaMachine : UIListener { UIElement* m_owner; SmartArray<MediaDesc*> m_array;
unsigned m_curIndex; }` (acclient.h:33873) is a **sequential program counter over
an opcode list**, not a state table.

`Update` (acclient.c:162444) executes `m_array[m_curIndex]`; each handler returns
*advance* (true) or *block* (false). On block, the loop breaks and the machine
calls `RegisterForGlobalMessage(3)` — global message 3 is the per-frame tick, and
`ListenToGlobalMessage` (acclient.c:162534) re-enters `Update`. **Animation
timing is cooperative and frame-driven, with no separate scheduler.**

The eleven `MD_Data_*` subclasses (acclient.h:34101–34181) have these numeric
opcodes, recovered from the dispatch at acclient.c:162444:

| Opcode | Type | Opcode | Type |
|---|---|---|---|
| 1 | Movie | 7 | Message |
| 2 | Alpha | 8 | Pause |
| 3 | Anim | 9 | Sound |
| 4 | Cursor | 0xA | State |
| 5 | Image | 0xB | Fade |
| 6 | Jump | | |

Control-flow semantics:

- **Pause** rolls a duration in `[m_minDuration, m_maxDuration]` on first
  execution, stamps `m_endTime`, and blocks until `Timer::compute_time()` passes
  it (acclient.c:162006).
- **Jump** is a probabilistic branch — `Random::RollDice(0,1) <= m_probability`
  then `m_curIndex = m_jumpItemIndex − 1` — and always advances, so loops are
  built from Jump-to-0 (acclient.c:162033).
- **Message** broadcasts `m_messageID` to the owner with probability
  `m_probability`, but only if owner flag bit 17 is set (acclient.c:162057).
- **State** probabilistically calls the owner's `SetState(m_stateID)` and then
  **always returns false**, halting the playlist. This is the state-transition
  primitive (acclient.c:162082).

`MediaMachine::Reset` (acclient.c:162572) deep-copies each descriptor via
`MediaDesc::CreateMediaType`, which is why per-instance mutable timing fields
(`m_endTime`, `m_StartTime`, `m_displayedFrameNum`) can live inside the
descriptor structs.

## 4. Paint pipeline

Painting is dirty-rect composition into per-window textures.

1. Widgets invalidate by pushing rects into `UIObject::m_dirtyRects`
   (`UIObject::AddDirtyRect`, acclient.c:689319).
2. Once per frame `UIElementManager::UseTime` (acclient.c:**153815**) runs
   delete-queue cleanup, mouse update, tooltips, and a global broadcast, then
   `DrawDirtyRegions` (acclient.c:152101), which recurses via `DrawRegion`
   (acclient.c:152085) into every element owning a `UIObject`.
3. `DrawRegionWithObject` (acclient.c:151289) hands the dirty boxes to
   `UIRegion::DrawHere` (acclient.c:696055), which intersects with the clip box
   and calls virtual `DrawSelf` then `DrawChildren` — or after children if
   `m_bDrawAfterChildren`. Base `UIRegion::DrawSelf` (acclient.c:695477) calls
   `Graphic::Draw` (acclient.c:683671) per dirty box, which clips, tiles, and
   `PutImage`s `RenderSurface` pixels into the window's `UISurface`.
   `UIElement_Text::DrawSelf` (acclient.c:164648) rasterizes glyph by glyph.
4. The `UISurface` — created in `UIElement::MakeUIObject` (acclient.c:158110) —
   keeps a local `RenderSurface`, a vertex buffer
   (`UISurface::SetupVertexBuffer`, acclient.c:124677), and a remote D3D texture.
   `UISurfaceObject::Render` (acclient.c:684129) uploads dirty texels, sets
   identity matrices, binds the texture, and draws an indexed **triangle-list
   quad** through `RenderUI::s_pUISurfaceIB`. Each top-level window is one
   texture and one quad.
5. `RenderUI::RenderObjects` (acclient.c:132950) walks the draw-ordered HashList
   `RenderUI::s_hlObjects`. Z-order within a parent is kept sorted at insert time
   by `CompareZLevel` in `UIRegion::AddChild` (acclient.c:696988), with
   `BringToFront` for activation. `RenderUI::ComputeGameViewport`
   (acclient.c:132983) shrinks the 3D viewport around edge-clamped panels.

Note this pipeline runs on the *second* renderer described in
`06-rendering.md` §2 — UI surfaces are the only live consumer of the modern
Turbine material stack.

## 5. Input routing, focus, drag-and-drop

Win32 messages enter at `Device::WndProc` (acclient.c:118421) and forward through
`Device::ForwardToInputManager` (acclient.c:117993) to
`CInputManager_WIN32::OnMessage` (acclient.c:673406). DirectInput devices are
also polled (`PollDevice`, acclient.c:669721).

`UIElementManager::OnAction` (acclient.c:155247) maps actions to mouse events —
but not symmetrically. The **press** path is `v2 > 4 && v2 <= 0xF →
MouseDownEvent` (acclient.c:155256–155259), i.e. **5–0xF** — and action **4 is
swallowed on the press path too** (`if (v2 == 4) return 1;`, 155254–155255),
which the "5–0xF" framing hides. The **release** path switch handles only
**5–0xC → MouseUpEvent**; actions 4, 0xD, 0xE, and 0xF are swallowed. Note also
that down passes `m_InputExtent` while up passes `m_pcCallback`.

Hit-testing is a template recursion, `MouseHitTester<MouseOverCriteria>::Recurse`,
over the z-ordered tree (`MouseMoveHandler`, acclient.c:155289; `MouseUpEvent`,
154697), honoring `m_bBlockClicks` and transparency.

`SetFocusElement` (acclient.c:152135) broadcasts message `0x2F` with dwParam 0 to
the outgoing element and dwParam 1 to the incoming one (acclient.c:152145,
152151), then calls an unnamed vtable slot on the incoming element with 3000
(`impri_FocusedUI`) at 152152 — reading that as `RegisterInputMaps` is a sound
inference, not a read symbol, and there is a symmetric `vfptr[15]` call on the
outgoing element.

**Drag-and-drop** (`StartDragandDrop`, acclient.c:154874) triggers when squared
distance reaches 16, i.e. a **4-pixel radius** (`(dx*dx + dy*dy) < 0x10` is the
reject test at acclient.c:**154921**). It also requires
`CInputManager::IsActionInProgress(cidm, 7u)` (acclient.c:154905) and that the
press point be inside the display.

The pressed element is asked via attribute `0x3A` ("dragable",
acclient.c:154926 — IDA even names the local `dragableProp`) to manufacture a
drag clone, which becomes a temporary root element owning its own `UIObject`,
moves with the mouse, and steals capture. On mouse-up, `MouseUpEvent` notifies
the drag *owner* with `NotifyMouseUp`.

**Tooltips**: `CheckTooltip` (acclient.c:152043) fires after `m_tooltipDelay` of
stillness; `StartTooltip` (acclient.c:154767) instantiates a tooltip *layout* from
the DAT, injects the `StringInfo`, and resizes. Tooltips are ordinary elements.

## 6. Two registries, and the full window roster

The first pass claimed all `gm*UI` are element classes in the `0x100000xx` range.
**That is wrong.** Login, chargen, and mode screens go through a **second,
independent registry**.

`gmUIFlow::gmUIFlow` (acclient.c:183742) calls `gmUIHelper::RegisterElements()`
for in-game widgets, then registers eight *screens* via
`UIFlow::RegisterFrameworkClass` (acclient.c:182722) at
acclient.c:183759–183766: `gmIntroUI 0x10000001`, `gmDisconnectedUI 0x10000002`,
`gmDataPatchUI 0x10000003`, `gmCreditsUI 0x10000005`, `gmGamePlayUI 0x10000008`,
`gmEpilogueUI 0x10000009`, `gmCharacterManagementUI 0x1000000A`,
`gmCharGenMainUI 0x1000000B`.

**All eight mode IDs collide with element classes**, not just one: `0x1`
BurdenIndicator, `0x2` EffectsIndicator, `0x3` LinkStatusIndicator, `0x5`
PortalStormIndicator, `0x8` gmPanelUI, `0x9` gmVitalsUI, `0xA` gmIndicatorsUI,
and `0xB` (unregistered as an element). Earlier drafts singled out `0x1000000A`,
implying the rest were clean. `gmCombatPanelUI`,
`gmSideVitals`, `gmStatManagementUI`, and `gmUI` have no `Register()` at all.

## 7. Input and keybinding

A raw control is a packed dword:
`ControlSpecification { m_idxDevice:8, m_eSubControl:8, m_ofsKey:16 }`
(acclient.h:27488–27502). A binding is a
`QualifiedControl { m_key, m_metamode, m_activation }` (acclient.h:**27512**) —
modifier state plus an activation bitmask, assembled in
**`CInputManager_WIN32::FireInputEvent` (acclient.c:672390)**. An earlier draft
named a function `ProcessControl` that **does not exist** in this binary.

The activation bits are: **1 press**, **2 release** (`DIDataToActivationType`,
669796), **4 tap** (672498, `<= sm_timeTap`), **8 double-click** (672519,
`sm_timeDoubleClick`), **`0x20` double-click-in-place** (672525, a `PtInRect`
against `sm_cxDblClick`/`sm_cyDblClick`), and `0x80` axis. Neither 8 nor `0x20`
is a "repeat qualifier". The composite `0xA9` is axis | dblclick-in-place |
dblclick | press.

Note the `ControlSpecification` bitfields `m_idxDevice:8 / m_eSubControl:8 /
m_ofsKey:16` live in an anonymous struct at acclient.h:27486–27488; `struct
ControlSpecification` itself (27499–27502) holds only a union.

**Two distinct DBObjs are involved**, not one:

- `ActionMap` (type 39 = `0x27`, DID `0x26xxxxxx`) is *metadata*:
  `HashList<mapID, HashList<actionID, ActionMapValue>>` plus `m_didStringTable`
  (localized action names) and `m_hashConflictingMaps` (acclient.h:27626). Loaded
  once as `DBObj::GetByEnum(1, 8, 0x27u)` in `CInputManager::OnStartup`
  (acclient.c:109950).
- `CMasterInputMap` (type 29 = `0x1D`, DID `0x14xxxxxx`) holds the actual
  key-to-action bindings. `AddKeyMap(actID)` fetches it via
  `DBObj::GetByEnum(_actID, 10, 0x1Du)` and merges (acclient.c:669991).

**Boot** is acclient.c:**62497–62506**: load the user file at 62501–62503, fall
back to `ClearKeyMap()` at 62504, then unconditionally merge the two DAT defaults
`AddKeyMap(0x10000001)` (62505) and `AddKeyMap(1)` (62506). **Shutdown** is
acclient.c:**61627–61641** — `SaveKeyMap` via vtable at 61640, `ClearKeyMap` at
61649, writing `CMasterInputMap::ToFileNode` (670548). (An earlier draft listed
these two ranges in the opposite order to the prose.)

**User bindings win per *control*, not per action.** The mechanism is
first-writer-wins: `HashList<QualifiedControl, unsigned long, 1>::push_tail`
(678222) on a duplicate key only calls `place_at_tail` (678243) and never
overwrites the value. But the hash key is the **control**, not the action — so
rebinding action A from K1 to K2 leaves the DAT's K1→A binding in place, and A
ends up on both keys.

**Toggle semantics.** `ActionMap::GetToggleType(action, mapID)` is consulted per
event in `CInputManager::FireActionEvent` (acclient.c:112031): 1 momentary
(auto-deactivates unless `m_activation & 0xA9`), 2 toggle, 3 one-shot — **the
default when the map has no entry** — 4 held-with-repeat, driven from
`CInputManager::UseTime` (acclient.c:111194) — **only type 4 enters the repeat
block** (`if (v9->m_toggle == 4)` at acclient.c:111278); type 5 is held but never
repeats — with
`sm_timeKeyRepeatDelay = 0.25 s` and `sm_timeKeyRepeatSpeed = 0.025 s`
(acclient.c:44762–44763). Actions **41, 42, 43** break run-lock
(acclient.c:112017).

**Input maps are a priority stack**, not a switch.
`RegisterInputMap(mapID, callback, priority)` inserts into a sorted list
(acclient.c:111176). `enum InputMapPriority` (acclient.h:5769):
`impri_Lowest 0`, `impri_Gameplay 1000`, `impri_UnfocusedUI 2000`,
`impri_FocusedUI 3000`, `impri_DebugConsole 4000`. Observed map IDs: 1, 7, and 8 (text editing and selection,
acclient.c:164158/164162/164168), 3 and 13 (`UIElementManager`,
acclient.c:155780–155781), 6 (mouse-look, priority 2000, acclient.c:147096), and
14 (`gmUIFlow`, priority 4000, acclient.c:183777).

**16 and 32 are not map IDs** — an earlier draft listed them as such. They are
bits of `RegisterInputHandler`'s third argument: `v3 & 0x10` adds to the
mouse-look list and `v3 & 0x20` sets `m_pKeyHitHandler`.

**Recovered InputAction IDs.** The camera block from `CameraManager::OnAction`
(acclient.c:146969): `0x33` closer, `0x34` farther, `0x35`/`0x36` rotate
left/right, `0x37` raise, `0x38` lower, `0x39` reset offsets, `0x3A` first person,
`0x3B` toggle look-down, `0x3C` toggle map mode, `0x3D` toggle mouse-look,
`0x3E` hold mouse-look. Elsewhere: **7** and **10** are mouse buttons
(acclient.c:519770), **39** (acclient.c:281963), **41/42/43** movement, **53**
rotate-left discriminator, **86** (acclient.c:680535), and **`0x1000005A`**
toggle combat (verified in `ClientCombatSystem::OnAction`, acclient.c:410080).

**Beware:** `0x1000005A` is *also* an unrelated UI **attribute** ID
(`m_dragScrollMarginHeight`, acclient.c:274592). Attribute and action IDs share
the `0x1000xxxx` shape but are different namespaces.

**Rebinding UI.** `UIOption_ActionKeyMap` (acclient.h:54392) holds
`m_idInputAction` / `m_idInputMap` plus three `List<QualifiedControl>` (defaults,
saved, current). `InitiateBinding` (acclient.c:197227) puts the manager into
key-capture mode via `RegisterInputHandler(this, 32)`; `KeyHitHandler`
(acclient.c:196988) rejects modifier-only and unbindable controls, then runs
`FindConflictingInputMaps` (acclient.c:669920) → `FindConflictingControls`
(acclient.c:671600) and raises `OpenOverwriteBindingDialog`
(acclient.c:196547) or `OpenCantOverwriteBindingDialog` (acclient.c:196872).

**IME/DBCS.** `WM_CHAR` (0x102) and `WM_SYSCHAR` (0x106) both funnel into the
lead-byte state machine at acclient.c:673488, holding `prevLeadByte` across two
messages and `MultiByteToWideChar`ing the pair. Full IME overlay is delegated to
`keystone.dll` (see `06-rendering.md` §12).

## 8. Camera

`CameraManager : CInputHandler, IInputActionCallback` (acclient.h:35238) is a
spring-damper follower: separate `t_stiffness` and `r_stiffness`, a pivot
object/part/offset, a target object/offset, a `CameraTarget` flag set
(`LOOK_AT_PIVOT`, `LOOK_AT_OBJECT`, `LOOK_IN_DIRECTION`, `ALIGN_WITH_PLANE`), a
5-sample velocity history for lead/lag, and `m_bAlignCameraToSlope`.

`CameraSet` (acclient.h:35361) is the mode layer: `looking_down`, `in_map_mode`,
`mouselook_active`, per-axis latch flags, and per-axis change timestamps.

**There is no discrete first/third-person enum.** First person is defined
geometrically: `CameraSet::InHead` returns true iff
`viewer_offset == (0, 0.18, 0)` (acclient.c:148203), and `SetInHead`
(acclient.c:149230) just writes that offset with translational stiffness 1.0.
`SetTargetForOffset` (acclient.c:148214) picks target flags from the offset's
quadrant — `y > 0` or `|x| > 1` implies `LOOK_AT_PIVOT`, as does
`z > 0.75 || z < −0.5`.

Zoom is geometric, and the two directions are **not** symmetric. `Closer` scales
by `1.0 − v8*0.2` (acclient.c:**149017**) and refuses to go inside radius 0.5
(**149022**). `Farther` uses the **opposite sign**, `v15*0.2 + 1.0` (**149105**),
and has **no radius guard at all** — it clamps `|x|,|y| <= 10` and `z <= 450`.
The `z <= −1.8 → stiffness 1.0` rule appears in both (149024 / 149112).

**Camera collision is a real physics sphere sweep.** `SmartBox::update_viewer`
(acclient.c:144991) builds `begin_pos` at the pivot and `end_pos` at the desired
camera point, then runs `makeTransition()` (145082) → `init_object(player, 92)`
(145086) → `init_sphere(1, &viewer_sphere, 1.0)` (145087) → `init_path` (145088)
→ `find_valid_position` (145089). The `viewer_sphere` radius is 0.3, at
acclient.c:**145543** (145537–145542 zero the sphere *origin*). On failure it
falls back to `CPhysicsObj::AdjustPosition`, and finally to snapping onto the
player.

Two corrections: `viewer_sought_position` is the **input** to `update_viewer`,
not the output — `set_viewer` is called with `set_sought_position = 0` on both
the success (145091) and `AdjustPosition` (145100) paths, and only the
player-snap fallback passes 1. And `SceneTool::SetupCamera` is **defined at
acclient.c:123180**; 144036 is a call site inside `SmartBox::set_viewer`.

Mouse-look: `CameraSet::MouseLookHandler` (acclient.c:149264) runs deltas through
`FilterMouseInput` (acclient.c:148138) — an EMA that only blends if the previous
sample was within 0.25 s — then scales by
`m_MouseLookSensitivity * 0.06666667` (1/15) and negates both axes when
`m_InvertMouseLookYAxis`. A 5-frame accumulator acts as a dead zone. With zero
delta and `m_UseMouseTurning`, it re-issues a turn command to the server at most
every 0.5 s.

## 9. Radar, map, toolbar, and the item-list drag protocol

### Radar

`gmRadarUI : UIElement_Field, gmNoticeHandler, QualityChangeHandler`
(acclient.h:54514) keeps a `SmartArray<RadarInfo>` where `RadarInfo` is
`{ACCWeenieObject*, RGBAColor, RadarBlipShape}` (acclient.h:54506). Only the
*object* is a live pointer; colour and shape **are** cached snapshots, refreshed
from `OnQualityChanged` (acclient.c:263725) and `RecvNotice_ChangeRadarLook`
(acclient.c:**263719**, a one-line adjustor thunk into
`gmRadarUI::UpdateRadarLook`, 263614).

`enum RadarBlipShape` (acclient.h:6575): 1 Circle, 2 Box, 3 X, 4 Plus, 5 Triangle,
6 InvertedTriangle, 7 XBox, with aliases Default = Plus, AllegianceMember = Box,
FellowshipLeader = Triangle, Fellowship = InvertedTriangle, Threat = X,
ThreatAllegiance = XBox. `GetBlipShape` (acclient.c:262864) resolves in priority
order: fellowship leader → fellow → allegiance → PK/PKL threat → default.

`GetBlipColor` (acclient.c:262708) first honours a server-authored
`pwd._blipColor` of 1–10, mapping in **switch** order to Blue, Gold, White,
Purple, Red, Pink, Green, Yellow, Cyan, BrightGreen. (The *declaration* order at
acclient.c:45107–45116 is different — Blue, Gold, Yellow, White, Red, Purple,
Pink, Green, Cyan, BrightGreen — so citing those lines for the sequence is
wrong.) Otherwise it falls through Portal → Vendor →
Creature → Admin → PlayerKiller → PKLite → Fellowship (acclient.c:53769–53781,
which also holds unreferenced Advocate, LifeStone, NPC, and Sentinel colours).

Blips are drawn as **raw `SurfaceWindow::FillArea` pixel runs** into the UI
surface, not sprites (`DrawPoint` at acclient.c:**262904**, plus `DrawEdges` / `DrawCorners` — 23
`FillArea` calls across 262904–263165, zero sprite blits), scaled by an intensity factor for altitude, and suppressed
wholesale by `ClientUISystem::m_bRadarBlank`.

### Map

`gmMapUI` is far simpler than expected: **no DAT map imagery lookup and no
zoom**. `PostInit` (acclient.c:218339) grabs a single child element
`0x100001EC` as `m_pMap` — its artwork comes from the layout like any other
element — reads four attributes `0x1000004E`–`0x10000051` as the marker rect,
loads one layout DID, and instantiates **53 hardcoded rollover regions** from
`s_rgLocations[53]` (acclient.c:39939) as tooltip children.

`PlaceMarkerOnMap` (acclient.c:218145) is more than the `(coord*10 + 1024)/2048`
normalisation earlier drafts gave. The actual arithmetic (218162–218168) is
`m_x0 + GetWidth/-2 − (int64)((m_x1 − m_x0 + 1) * (x*10 + 1024) * −0.00048828125)`,
and **Y is inverted** via `2047.0 − (y*10 + 1024)`. The `/2048` term is only the
normalised factor; the marker-rect span scaling, half-marker centering, and Y
flip all matter. Only two markers exist: `m_pPlayerLocationIcon` and
`m_pHouseLocationIcon`. Dungeon maps are not part of this window.

### Toolbar and shortcuts

Persistence is `ShortCutManager { ShortCutData* shortCuts_[18] }` inside
`PlayerModule` — 18 item slots — with spell shortcuts held separately as
`favorite_spells_[8]`. See `03-object-model.md` §11.

The UI side is elegant: `gmToolbarUI::m_shortcutSlots` is a
`SmartArray<UIElement_ItemList*>` — **each toolbar slot is a one-item
`UIElement_ItemList`** (acclient.h:55080). That is why drag-to-toolbar needs no
special case; it is the ordinary item-list drop protocol.

`UseShortcut` (acclient.c:239995) pulls item 0 from the slot's list and branches
three ways: if `ClientUISystem::targetMode` is set, `ExecuteTargetModeForItem` and
clear target mode; else `ItemHolder::UseObject`; else just `SetSelectedObject`
(acclient.c:240017–240033). `RecvNotice_FullMergingItem` (acclient.c:241250)
transparently re-points a shortcut when a stack merges;
`RecvNotice_ItemListBeginDrag` (acclient.c:240399) removes the shortcut as soon
as the drag leaves the slot.

### `UIElement_ItemList` and drops

The container model is an explicit doubly-linked chain — `parentContainerID`,
`childList`, `parentList` — so a backpack inside a backpack is a second
`UIElement_ItemList` hung off the first, not a tree rebuild.

Four exclusive mode booleans (`containerList`, `vendorItemList`, `shortcutList`,
`salvageList`) drive every behavioural difference. The three non-container modes
skip `SetWaitingState` (no server round-trip is pending), and
`CM_Item::SendNotice_BeginDrag` is told `vendor || salvage || shortcut` so
downstream systems know the drag is virtual (acclient.c:273362–273367).

The grid is `m_cellW` × `m_cellH` with a `List<UIElement_UIItem*>
m_listUIItemCache` recycling cell widgets. Drag-scroll is fully parameterised:
`m_dragScrollMarginWidth` / `Height` (attributes `0x10000059` / `0x1000005A`),
`m_dragScrollJumpDistance`, `m_dragScrollDelay`.

The drop protocol is a one-method interface:
`ItemListDragHandlerVtbl { bool OnItemListDragOver(UIElement_UIItem*, dropItemID,
dropSpellID, DropItemFlags) }` (acclient.h:54242). `DropItemFlags`
(acclient.h:6765) is `NONE 0`, `IS_CONTAINER 1`, `IS_VENDOR 2`, `IS_SHORTCUT 4`,
`IS_SALVAGE 8`, `IS_ALIAS 0xE`.

`UIElement_ItemList::ItemList_DragOver` (acclient.c:273375) calls the registered
handler first; **returning true means "handled, stop"** — the base implementation
just returns 0 (acclient.c:219666). Only if unhandled *and* the list is a plain
inventory container does the list itself set the visual state. There are
**three**, not two: reject `0x10000041` (acclient.c:**273418**), accept
`0x10000040` (**273426**), and — for a container with empty slots —
`0x10000046` (**273432**).

Implementors: gmToolbarUI, gmPaperDollUI (which registers exactly **24**
equipment slots individually at acclient.c:**221402–221594**; 219720+ is the
*un*register teardown), gmSalvageUI, gmSecureTradeUI,
gmSlumlordUI, gmExternalContainerUI, VendorSellUI, SpellCastSubMenu.

## 10. Options round-trip

Every `UIOption_*` carries the same triple — `m_default`, `m_saved`, `m_current`
— plus three mutually exclusive persistence targets (acclient.h:55696):
`m_propName` (a `BaseProperty` name), `m_playerOption` (a `PlayerOption` enum),
and `m_prefName` (a client-local string key).

`UIOption_Checkbox::Apply` (acclient.c:**194447** — 194279 is inside
`ListenToElementMessage`) dispatches in exactly that order:
`m_propName` → `PlayerModule::SetOption(BaseProperty)`; else
`m_playerOption != −1` → `PlayerModule::SetOption(enum, value)`; else
`UIPreferences::ModifyPreference(m_prefName, m_current)` (acclient.c:194550).
`SetUIPreference` (acclient.c:194403) is a no-op unless the first two are unset,
and pulls label and tooltip string IDs from the preference registry
(`UIPreferences::InqPreference`, acclient.c:520364; the registry is a
`HashTable<PStringBase<char>, UIPreferenceItem*>` at acclient.c:45881).

`OptionPage : UIElement, IOptionChangeHandler` owns a `SmartArray<UIOption*>` and
fans Save / Restore-Saved / Restore-Default across it; `PlayerOptionPage` adds a
listbox. `UIOption_CheckboxBitfield64` (acclient.h:55766) is a listbox of
`ChildInfo { __int64 llMask, StringInfo siLabel, StringInfo siTooltip }` rows
editing one 64-bit word — which is how the chat window's `m_llTextTypeFilter` is
authored.

## 11. Fonts and text

`Font : DBObj` (acclient.h:38822) is a **bitmap atlas**, not a vector font: a
foreground `RenderSurface` and a separate background/shadow surface,
`maxCharHeight` / `maxCharWidth`, `m_BaselineOffset`, and border pixel counts.

Per-glyph metrics are `FontCharDesc { m_Unicode, m_OffsetX, m_OffsetY, m_Width,
m_Height, m_HorizontalOffsetBefore, m_HorizontalOffsetAfter,
m_VerticalOffsetBefore }` (acclient.h:38812) — an 11-byte packed record.

**There is no pair kerning.** The only "kerning" is per-glyph side bearings;
`tagKERNINGPAIR` (acclient.h:**22524**) is unused by code, though
acclient.h:60353 does `typedef tagKERNINGPAIR *LPKERNINGPAIR;`. Advance is the
three-term per-glyph sum `m_Width + m_HorizontalOffsetBefore +
m_HorizontalOffsetAfter` (127398, 126960); no `GetKerningPairs`,
`GetCharABCWidths`, or two-glyph lookup exists. Unicode lookup
is a dense `characterMap[chr − minUnicodeChar]` index with a range guard
(`Font::GetCharDesc`, acclient.c:**127341** — an earlier draft cited 290570,
which is inside `CLCache::WorkerExecuteRequest`, 163k lines away). On a miss it
retries once with `'?'` (63). `FontLocal` is a per-language subclass
with its own DID band.

Layout is `GlyphList` (acclient.h:45305): a `List<Glyph>` where each `Glyph`
carries its **own** `Font*`, `RGBAColor`, and `TextTag*` (acclient.h:45330) — so
colour, font, and hyperlink change mid-run without markup — plus a derived
`SmartArray<GlyphLine>`.

`GlyphList::Recalculate` (acclient.c:176539) memoises against
`m_cxLastRecalcWidth` / `m_bOneLine` and only rewraps when width or single-line
mode actually changed; `m_nFirstInvalidPosition` bounds incremental relayout, and
`m_bTrimFromTop` implements the scrollback ring for chat logs. The same
`GlyphList` powers the `DebugConsole` (acclient.h:45390).

## 12. `UIElement_Browser` — a real embedded browser

`UIElement_Browser : UIElement, IAlternateDCProvider, IBrowserCallback`
(acclient.h:53534). The constructor does `LoadLibraryA("Trowser.dll")` and
`GetProcAddress(..., "CreateBrowserControl")`, caching both in statics
(acclient.c:167776–167784).

The callback interface is verbatim `DWebBrowserEvents2`: `BeforeNavigate2`,
`DownloadBegin`, `ProgressChange`, `DownloadComplete`, `NavigateComplete2`,
`NavigateError`, `DocumentComplete`, `TitleChange` (acclient.h:53516–53525). So
`Trowser.dll` is a Turbine wrapper around the IE/MSHTML `WebBrowser` control.

Rendering is a **real child HWND, DC-redirected into the UI surface**.
`CreateWindowHelper` (acclient.c:167873) creates the browser window as a child of
`Device::m_hWnd` at the element's screen rect, then calls
`RedirectWindowDC_Thunk(hwnd)`; `UIElement_Browser::ReleaseDC`
(acclient.c:167916) is the `IAlternateDCProvider` hook marking the owning root
dirty whenever the browser paints.

Because a child HWND cannot coexist with exclusive fullscreen, a static
`sm_cVisibleWindows` refcount calls `Device::AllowFullScreenMode(0)` on the first
visible browser and `(1)` when the last hides, unless `m_fAllowFullscreenBrowser`
(acclient.c:167808–167839).

Navigation is data-driven: setting attribute **173** passes the string straight to
the control's navigate method (`OnSetAttribute`, acclient.c:168029).

## 13. Localization and chat

`StringInfo` (acclient.h:30308) references a `StringTable : DBObj`
(acclient.h:48678) by table DID plus string ID, with variables and a literal
override. `StringTableMetaLanguage` (acclient.c:13204–13235) is a mini parser and
renderer supporting escapes, gendered "meta letters", singular and plural forms,
capitalization, and variable substitution.

### Chat pipeline

`ChatInterface::ProcessCommand` (acclient.c:288749) reads the entry text, passes
it to `ClientCommunicationSystem::OnChatCommand` (acclient.c:426126), and keeps a
**100-entry** history — appending, resetting `m_LastInputHistoryPos = −1`, and
trimming from the front while `m_num > 0x64` (acclient.c:288777–288784).

`OnChatCommand` first offers the line to the Decal plugin hook, then narrows to a
`PStringBase<char>`, trims whitespace both ends, and normalizes:

- `case 47` (`/`) → `SetAtIndex(0, 64)` making it `'@'` → `DoCommand`
- `case 64` (`@`) → `DoCommand` directly
- `case 58` / `59` (`:` / `;`) → **replaces the leading char with a space (32)**
  and *prepends* the literal `"@emote"` before `DoCommand`

Plain text becomes speech. Inbound display goes through
`ClientSystem::AddTextToScroll` (acclient.c:401102): offered to the plugin with
an "eat" flag, profanity-filtered via `TabooTableAdaptor::CheckCensorsW`,
optionally timestamped, logged, then broadcast as
`ECM_UI::SendNotice_DisplayFinalStringInfo`.

Each `ChatInterface` filters by a **64-bit** `m_llTextTypeFilter`
(acclient.h:54907); `TypeIsActive` (acclient.c:287014) tests `1i64 << i_ltt`
against both halves. Default init sets all 64 bits then clears bit 26
(acclient.c:288224–288233).

Clickable content is embedded as `TextTag`s attached to glyphs — `TextTag_DID`,
`TextTag_IID`, `TextTag_IIDEnum`, `TextTag_IIDString`.

## 14. The notice system

`NoticeRegistrar` (acclient.h:30245) holds a
`HashTable<unsigned long, List<NoticeHandler*>*, 0>*` — a pointer to a table of
*pointers* to lists — built lazily on first registration
(`RegisterNoticeHandler`, acclient.c:121454).

Crucially, `CWeenieObject : LongHashData, NoticeRegistrar` (acclient.h:30252) —
**every game object is itself a notice registrar**, alongside the process-wide
`GlobalEventHandler::GetGlobalEventHandler` (acclient.c:121069). Note 183629 is
`gmGlobalEventHandler`'s **constructor**, not a singleton accessor.

Each `SendNotice_X` is generated boilerplate: fetch the handler list for a
compile-time constant ID, and for every handler call vtable slot 0 (an
is-being-deleted guard, at 182911) and then a **fixed vtable slot** — e.g. `+532`
at 182912, in `CM_UI::SendNotice_ClearChatBuffer` (body 182894–182916; note it is
a `SendNotice_`, and the class is `CM_UI`). There is no dynamic
dispatch table; the notice ID and vtable offset are both baked in, which is why
`gmNoticeHandler` (acclient.h:37233) is an empty subclass whose entire content is
a roughly 160-entry vtable.

**Navigational fact worth knowing first: the 5100xxx IDs are address-encoded in
the decompilation.** `SendNotice_ClearChatBuffer` does not contain a decimal
literal; it decompiles as `(unsigned int)((char *)&loc_4DD250 + 2)`, i.e.
0x4DD250 + 2 = 5100114. Grepping for the decimal will find nothing.

IDs fall in **two** bands:

- **100000–100023** — engine-level `ECM_*`: 100000 ServerDied, 100001
  CharacterError, 100002 WorldName, 100003/100004 Open/CloseDialog, 100005
  DisplayStringInfo, 100006 CharacterSet, 100007 SmartBoxObjectFound, 100008
  ServerSaysMoveItem, 100009 ServerSaysAttemptFailed, 100010 SetSelectedItem,
  100011 ItemAttributesChanged, 100013 UpdateGameView, 100014 CreateObject,
  **100015 `ECM_Physics::SendNotice_BeingDeleted`** (682291, omitted by earlier
  drafts), 100016 PlayerObjDescChanged, 100017 RuntimeDDDStatus, 100018–100021
  TextTag click notices, 100022 DisplayFinalStringInfo, 100023
  DisplayWeenieError. (100012 is genuinely unused; 100023 is the maximum.)
- **5100001–5100164** — gameplay `CM_*`, in rough subsystem runs: 5100016
  PlayerDescReceived, 5100027 SetCombatMode, 5100033 EnchantmentsChanged, 5100046
  OpenVendor, 5100047–5100052 fellowship, 5100081–5100090 trade, 5100091–5100096
  chess, 5100098 RefreshActionKeyMapping, 5100106–5100111 spell navigation,
  5100114 ClearChatBuffer, 5100118 ItemListBeginDrag, 5100124
  UpdateRadarVisibility, 5100143–5100149 friends, 5100159–5100162 contracts,
  5100163/5100164 Save/LoadUI. (Two range labels in earlier drafts were wrong:
  5100144 is `SetChatWindowTitle` and 5100145 is `StartTell`, not friends; 5100160
  is unused; and trade starts at 5100080 `RegisterTrade`.)
There are **no out-of-band outliers.** An earlier draft listed "6289 / 6290" for
AbuseReportResponse and OpenSalvagePanel; that was `nullsub_1891` — IDA's decimal
autoname counter — misread as hex. `CM_Character::SendNotice_AbuseReportResponse`
(699032) dispatches on `(unsigned int)nullsub_1891`, whose address is given at
acclient.c:238917 as **0x4DD221 = 5100065**, and `SendNotice_OpenSalvagePanel`
uses `nullsub_1891 + 1` = **5100066**. Both are in band.

**157** `SendNotice_*` symbols exist. For `RecvNotice_*` there are 154 distinct
tokens but only **152 with definitions** — `RecvNotice_OpenDialog` and
`RecvNotice_TextTag_DIDClick` appear only as `NoticeHandlerVtbl` member names.

One caution: the "roughly 160-entry vtable" figure for `gmNoticeHandler` is *not*
in the header. The only declared vtable is `NoticeHandlerVtbl` (acclient.h:30217)
with **21** slots; 160 distinct call-site offsets (max +692, implying ≥174
entries) is an inference from usage.

## 15. Plugin surface
